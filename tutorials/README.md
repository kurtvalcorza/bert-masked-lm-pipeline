## Conformance notes

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/bert_masked_lm_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 8-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision generated from, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/bert_masked_lm_input_manifest.json` and covers **both** capabilities in one manifest — the batch `embed` would take, with every entry carrying a `[MASK]` additionally checked against `fill_mask`'s contract and marked `fill_mask_input` — plus the schema, ceilings, verdict and one recorded rejection finding (a two-mask text); `evaluation_report` (EVAL21) writes `outputs/bert_masked_lm_evaluation_report.json`, whose verdict is always `not-measurable` because neither capability has a metric helper here. Supplying the author's expected token does not change the verdict: one expected token is an intent, not a labelled cloze set, and the report says so in `reason` rather than presenting a single observation as an accuracy (EVAL9).
- The notebook exercises `BERTMaskedLMPipeline` carried verbatim in the notebook rather than reimplementing model loading; the pipeline pins the immutable upstream revision, stages the missing snapshot file through the package's `stage_missing_files(..., allow_download=True)`, loads only from a digest-verified local snapshot (`verify_snapshot`), and refuses remote model code. No cell outside the carried module calls `transformers` or `huggingface_hub`.
- Two capabilities in one `TASK-INFERENCE` notebook, each with its own stated input/output contract (INF10): `fill_mask` (Section 6) and `embed` (Section 7) share the model, the ceilings and the export, and neither produces an artifact.
- Score semantics (UNC1–UNC4): the fill-mask `score` is a softmax over the 30,522-token vocabulary at the masked position — a ranking signal, not a calibrated probability; the default decision rule is `argmax` (first candidate); the pipeline ships no threshold and the caller owns any cut-off.
- §20.6 embeddings: shape `(N, 768)` and the pooling policy (`cls` position or attention-masked `mean` of the last layer, then L2 normalisation) are stated; the unit is one vector per text; missing data has no meaning (empty strings are rejected, over-long texts are rejected rather than truncated); embeddings are representations, not predictions; identifiers are exported alongside vectors in `outputs/bert_masked_lm_embeddings.csv`.
- No intrinsic metric exists (EVAL9): the repository ships no metric helper; the notebook says so for both capabilities, names what a real evaluation needs (a labelled cloze set for top-k hit rates; a judged similarity or retrieval set for Spearman/recall@k), and presents the expected-token check and the cosine table as falsifiable plumbing/qualitative checks only. The model card's smoke observations are quoted as one measurement, not expected values. Recorded `SHOULD` deviation: EVAL11 (no baseline — none is meaningful without labels).
- Ceilings `MAX_TEXT_CHARS`, `MAX_TEXT_TOKENS` (reject, never truncate), `MAX_BATCH`, `MAX_TOP_K`, `MASK_TOKEN` (exactly one), `POOLINGS`, `VOCAB_SIZE`, `HIDDEN_SIZE` are surfaced before the model runs (DAT22/DAT23).
- The default sample is synthetic text authored in code; `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
